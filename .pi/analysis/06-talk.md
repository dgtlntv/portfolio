# Talk — Content Analysis & Restructuring Plan

## Current State

This reads as a technical concept project from university. It's interesting as an idea, but it demonstrates almost no professional design skills — no user research, no stakeholder management, no iteration based on feedback, no real-world validation. It's essentially: "I had an idea → I built it → here's how it works → here's what it could do."

For a portfolio targeting hiring managers, this is the weakest project. That's not because it's bad work — it's because it's structured as a technical demo rather than a design project.

## What It Currently Communicates

- You can think conceptually about problems
- You have technical skills (NLP, speech-to-text, ML)
- You can build functional prototypes
- You're interested in challenging existing paradigms

## What It Should Also Communicate (if restructured)

- How you validated (or didn't validate) the problem
- What the design process looked like, not just the technical implementation
- How you tested the concept with actual people
- What worked, what didn't, and what you learned

## Section-by-Section Analysis

### 1. Problem (decent framing, but unsupported)
The "Death by PowerPoint" framing is relatable and the Tufte/NASA reference adds weight. But the problem is stated as self-evident rather than investigated.

**Content to add:**
- **Did you validate this problem beyond personal experience?** Even informal conversations with classmates, professors, or professionals about their presentation pain points would count. If you didn't do any validation, be honest about it — "This was driven by personal frustration rather than formal research, which I'd approach differently today." That kind of reflection shows growth.
- **What specifically about presentations is the problem?** You mention "poor slide design and rigid navigation" but there's a tension in your project: is the problem that PowerPoint is a bad tool, or that people use it badly? Your solution assumes the tool is the problem. Did you consider that the issue might be presentation skills, not software?

### 2. The Concept (clear, keep)
The explanation of Talk — presentation system that responds to speech — is clear and compelling as a concept.

**Content to add:**
- **How did you arrive at this specific solution?** You jump from "presentations are bad" to "here's my speech-driven system." What alternatives did you consider? What if you'd focused on better templates? Or a tool that coaches presenters? Or a collaborative presentation tool? Showing the solution space you explored demonstrates design thinking, even retroactively.

### 3. How It Works (good explanation, but it's all mechanism)
The script-linking system, semantic analysis, and linguistic emphasis → visual hierarchy translation are well-explained. The example ("We are going to implement X and Y...") is effective.

**Content to add:**
- **Did you test this with anyone?** Did you watch someone try to set up a Talk presentation? Did you observe whether the speech-to-navigation actually worked in practice? Even a single user test would add enormous value to this case study. If you didn't test it, reflect on that.
- **What were the design decisions in the presentation output?** You describe how speech maps to visualizations, but what did those visualizations look like? What visual design system did Talk use? How did you decide what "emphasis" and "de-emphasis" looked like visually?

### 4. Technical Implementation (trim)
This section is more relevant to an engineering portfolio than a design portfolio. Keep it brief — the NLP capabilities list is sufficient.

### 5. Results (currently a bullet list of theoretical benefits)
The results are stated as features/capabilities, not observed outcomes. "Presenters could address audience questions instantly" — did they, or is this hypothetical? The current framing makes it hard to tell.

**Content to add — and this is the most important addition:**
- **Be honest about the level of validation.** If this was a working prototype that you demonstrated but didn't formally test, say so. If you did present with it, describe the experience. What worked? What broke? What surprised you?
- **What would you do differently with your current skills?** This is a bachelor's thesis from 2021. You now have significant professional UX experience. How would you approach this project today? Would you start with user research? Would you test the core assumption (that automated navigation is better than manual) before building? This reflection turns a student project into evidence of professional growth.

## Process Line Stages for This Project

```
Experiencing the problem → Researching the landscape → Concepting a solution → Designing the system → Building the prototype → Demonstrating
```

The line for this project should be relatively simple and linear — because the process *was* simple and linear. That's okay. Being honest about a straightforward concept-to-prototype flow is better than pretending there were iteration cycles that didn't exist. If you add a reflection section, the line could have a dashed "looking back" loop at the end.

## The Bigger Question: Should This Project Stay?

Honestly, this project is on the fence. It's interesting conceptually but it doesn't serve your portfolio's goal of demonstrating professional design competency. You have two options:

**Option A: Keep it, but add a reflective lens.** Frame it explicitly as a student project and add a "What I'd do differently today" section. This turns it from a technical demo into a growth narrative. It shows self-awareness and how your thinking has matured.

**Option B: Move it to a secondary section.** Put it in a "Side Projects" or "Experiments" area alongside MLRUG, separate from your professional case studies. This keeps it accessible for people who are curious, without it competing with your Canonical work for attention.

I'd lean toward **Option B**, but if you go with Option A, the reflective addition is non-negotiable.

## Priority Level for Rewrite

**Low.** Spend your time on Proto*, Figma Libraries, MAAS, and Design Tokens first. Those are the projects that will get you hired. Talk should only be revised after those are strong.
